# Списки в адмінці будуються через DynamoDB Scan — виняток із Закону №8

Конституція бекенду забороняє `Scan` на request-path, а індексу «всі Салони / всі Майстри» в single-table немає (лише GSI1 `CITY#<cuatm>` і cron-снапшот активних лістингів). Для `admin-api` ми свідомо робимо виняток: списки профілів отримуються Scan-ом із фільтром `sk = PROFILE`, результат кешується на хвилини, пошук і сортування виконуються в браузері. Користувач один, трафік мізерний, а новий GSI з бекфілом — непропорційна ціна на старті.

## Considered Options

- **Розріджений GSI-ключ на профілях** (`ENTITY#SALON` + `createdAt`) з бекфіл-скриптом — правильне довгострокове рішення, відкладено.
- **Список через наявний `CITY#`** — відхилено: не показує профілі без міста, Заблоковані й Видалені, незручний для пошуку за назвою.

## Consequences

- Виняток діє **лише** в `admin-api`; у client-api, salon-api та master-api Закон №8 лишається без змін.
- Вартість Scan росте з кількістю Записів у таблиці, а не Салонів. Тригер перегляду: список вантажиться довше 3 с або таблиця перевищує 1 ГБ → переходимо на розріджений GSI.
