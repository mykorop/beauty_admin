# Адмінка працює через окремий сервіс `admin-api` у бекенді

Наявні ендпоінти бекенду жорстко прив'язані до `sub` того, хто викликає (`salonId = userId`), тож Адміністратор платформи не може ними змінити чужий Салон. Ми додаємо четвертий сервіс `services/admin-api` у `bookme-backend`: нова роль `admin` у `custom:role` того самого Cognito-пулу, шляхи `/admin/*` дзеркалять salon-api/master-api з явним `salonId`/`masterId` у шляху й перевикористовують ті самі Zod-схеми та сервіси домену. Так Адміністратор платформи діє «як власник будь-якого Салону» й автоматично підкоряється всім інваріантам конституції, а кожна зміна має справжнього автора для Журналу дій.

## Considered Options

- **Прямий доступ адмінки до DynamoDB** — відхилено: обходить сервісний шар із ~40 інваріантами (lock «один салон на майстра», слот-lock-и, search-проєкція, правило «тиждень майстра всередині тижня салону»); одна необережна правка ламає бронювання.
- **Імперсонація** (токен від імені Власника салону + наявні ендпоінти) — відхилено: немає крос-салонних списків, а в Журналі дій неможливо чесно відрізнити адміна від власника.

## Consequences

- Адмінка не може з'явитися раніше за відповідні ендпоінти `admin-api`; робота йде вертикальними зрізами в двох репозиторіях. Контракт описує плейбук `admin.md` у конституції бекенду.
- CORS `admin-api` — allowlist лише на origin-и адмінки (на відміну від `*` у salon-api/master-api); акаунт `admin` створюється вручну, без самореєстрації, з обов'язковим TOTP MFA.
- Адміністратор платформи не порушує закони домену: не прив'язує Майстра без Інвайту, не вилучає Власника-майстра, не каскадує ціни на Копії майстра. Email/телефон/пароль акаунтів лишаються поза адмінкою.
