# 06: Редагування профілю Салону + Журнал дій

**What to build:** Адміністратор платформи змінює поля профілю Салону й зберігає. Зміна потрапляє в Журнал дій і одразу видна на вкладці «Історія». Якщо Власник салону встиг змінити профіль — адмін бачить «дані змінились, перезавантажте». Тут народжується вся інфраструктура записувальних дій.

**Blocked by:** 04 (Картка Салону: перегляд); 05 (Префактор: сервіси домену Салону приймають `salonId`)

**Status:** ready-for-agent

Специфікація: `../spec.md` · Словник: `CONTEXT.md` · ADR: `docs/adr/`. Тикет зачіпає обидва репозиторії (`bookme-backend` → `admin-api`, `beauty_admin` → UI), якщо не сказано інше.

- [ ] `PATCH /admin/salons/{salonId}/profile` використовує ту саму схему й сервіс, що salon-api; редагуються назва, опис, адреса, контактний телефон салону, буфер, горизонт бронювання, колір бренду
- [ ] Email, телефон і пароль акаунта в UI лише для читання
- [ ] UI надсилає лише змінені поля
- [ ] Запит несе `updatedAt`, який бачив адмін; розбіжність → відмова новим стабільним кодом конфлікту; умова перевіряється самим записом у DynamoDB
- [ ] Рядки Журналу дій: незмінні, без TTL, у тій самій таблиці; партиція на ціль + глобальний ключ за часом; поля — адмін, тип і id цілі, контекстний Салон, тип дії, час, змінені поля (старе → нове), причина
- [ ] Запис у Журнал — в одній транзакції зі зміною; відхилена дія рядка не створює; операцій зміни чи видалення рядків Журналу не існує
- [ ] Чистий модуль diff-а («до» + «після» → змінені поля) з юніт-тестами: вкладені об'єкти, масиви, поле зникло, поле з'явилось, без змін
- [ ] Значення змінених полів не потрапляють у логи CloudWatch
- [ ] `GET /admin/audit?target=…` і вкладка «Історія» на картці; повні значення, зокрема PII, без маскування
- [ ] Будь-яка записувальна дія над Видаленим Салоном відхиляється
- [ ] Jest: успіх + рядок Журналу з правильним diff-ом, конфлікт, відмова домену без рядка Журналу; Playwright: PATCH лише змінених полів, сценарій конфлікту
