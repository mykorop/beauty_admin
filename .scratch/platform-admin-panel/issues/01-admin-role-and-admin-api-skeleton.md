# 01: Роль `admin` і кістяк `admin-api`

**What to build:** У `bookme-backend` з'являється четвертий сервіс `admin-api` (ADR-0001) з єдиним ендпоінтом `GET /admin/me`, який повертає ідентифікатор і email Адміністратора платформи. Роль `admin` стає допустимим значенням `custom:role` у спільній бібліотеці. Це перша точка, через яку можна переконатись, що адмін-токен приймається, а будь-який інший — ні.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

Специфікація: `../spec.md` · Словник: `CONTEXT.md` · ADR: `docs/adr/`. Тикет зачіпає обидва репозиторії (`bookme-backend` → `admin-api`, `beauty_admin` → UI), якщо не сказано інше.

- [ ] Роль `admin` додана до типу ролей і Zod-схеми ролей; наявний тест, що стверджував протилежне, оновлено
- [ ] Сервіс `admin-api` збирається й деплоїться за зразком трьох наявних, входить у compose-деплой
- [ ] `GET /admin/me` з токеном ролі `admin` повертає 200 у стандартному конверті відповіді
- [ ] Той самий запит із роллю `client`, `salon` чи `master` повертає 403, без токена — 401
- [ ] CORS — allowlist лише origin-ів адмінки (dev, prod, localhost), не `*`
- [ ] У конституції бекенду створено плейбук `admin.md` із загальними правилами контракту `/admin/*`: ідентифікатор сутності зі шляху, ніколи з токена; перелік свідомо відсутніх ендпоінтів зі специфікації
- [ ] Задокументовано ручне створення користувача-адміна в Cognito з обов'язковим TOTP MFA
- [ ] Jest-тести на рівні хендлера покривають усі чотири ролі й відсутність токена
