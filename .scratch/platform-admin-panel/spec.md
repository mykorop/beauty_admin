# Панель Адміністратора платформи BookMe

Status: ready-for-agent

Словник — `CONTEXT.md`. Архітектурні рішення — ADR-0001 (`admin-api`), ADR-0002 (Scan для списків), ADR-0003 (статистика на вимогу). Канон домену — конституція `bookme-backend` (`project-constitution/`); ця специфікація його не дублює і не змінює.

## Problem Statement

У команди BookMe немає жодного способу побачити платформу цілком. Кожен ендпоінт бекенду прив'язаний до акаунта того, хто його викликає, тож Салон бачить лише себе, Майстер — лише себе, а людина з команди не бачить нікого. Щоб дізнатись, скільки Салонів зареєстровано, хто кинув реєстрацію на півдорозі, чому Клієнт не може записатись, або виправити помилку в Годинах роботи на прохання Власника салону, сьогодні треба лізти в DynamoDB-консоль чи писати одноразовий скрипт. Немає способу прибрати недоброчесний профіль із пошуку, приховати образливий відгук чи видалити неприйнятне фото. Майстри салону, чий Салон видалив акаунт, застрягають назавжди прив'язаними до нього — і звільнити їх нічим.

## Solution

Десктопна веб-адмінка для одного Адміністратора платформи. Після входу з MFA він бачить дашборд із Базовими показниками, звідки одним кліком переходить у списки Салонів, Незалежних майстрів, Клієнтів, Записів і Відгуків. Усередині Салону він бачить усе, що бачить Власник салону: профіль, Години роботи, Ростер, Каталог послуг, Записи, відгуки, фото, сертифікати, Інвайти — і може це змінювати, діючи «як власник будь-якого Салону» в межах законів домену. Він може Заблокувати профіль із причиною, масово скасувати майбутні Записи, приховати відгук, видалити фото, вилучити Майстра з Ростеру. Кожна його зміна потрапляє в незмінний Журнал дій. Детальну статистику (ріст, Записи, Вартість Записів, топи, «Потребують уваги») він запускає на вимогу й отримує цифри з живих даних.

## User Stories

### Вхід і каркас

1. As an Адміністратор платформи, I want to увійти email-ом і паролем із обов'язковим TOTP-кодом, so that до даних усіх Салонів не потрапив сторонній, навіть знаючи пароль.
2. As an Адміністратор платформи, I want to щоб акаунт із будь-якою роллю, крім `admin`, отримував відмову при вході в адмінку, so that Власник салону чи Клієнт не могли зайти сюди зі своїми обліковими даними.
3. As an Адміністратор платформи, I want to щоб сесія тихо оновлювалась, а після її спливу мене повертало на екран входу з поверненням на ту саму сторінку, so that я не губив контекст роботи.
4. As an Адміністратор платформи, I want to вийти з адмінки однією кнопкою, so that залишити робоче місце безпечним.
5. As an Адміністратор платформи, I want to перемикати мову інтерфейсу між українською, російською й румунською, so that працювати зручною мовою; вибір зберігається в браузері, за замовчуванням — українська.
6. As an Адміністратор платформи, I want to бачити контент (назви, описи, відгуки) тією мовою, якою його написали, so that не читати машинний переклад.
7. As an Адміністратор платформи, I want to постійне бокове меню: Дашборд, Салони, Незалежні майстри, Клієнти, Записи, Відгуки, Журнал дій, so that дістатись будь-якого розділу з будь-якого екрана.
8. As an Адміністратор платформи, I want to бачити в шапці, з яким середовищем (dev / prod) я працюю, so that не змінити продакшн-дані, думаючи, що це тест.
9. As an Адміністратор платформи, I want to щоб кожна відмова бекенду показувалась зрозумілим повідомленням за її `error.code`, so that розуміти, який саме закон домену не дав зберегти зміну.

### Списки Салонів і Незалежних майстрів

10. As an Адміністратор платформи, I want to бачити таблицю всіх Салонів: назва, місто, Власник салону, рейтинг, кількість відгуків, стан, дата реєстрації, so that охопити платформу одним поглядом.
11. As an Адміністратор платформи, I want to таку саму таблицю Незалежних майстрів, so that бачити бізнеси без Салону окремо.
12. As an Адміністратор платформи, I want to шукати в таблиці за назвою, email-ом, телефоном, so that знайти профіль зі звернення в підтримку.
13. As an Адміністратор платформи, I want to фільтрувати за станом (активний / Заблокований / Видалений) і за містом, so that працювати з потрібним зрізом.
14. As an Адміністратор платформи, I want to сортувати за будь-якою колонкою, so that знаходити найновіші чи найгірше оцінені профілі.
15. As an Адміністратор платформи, I want to бачити Видалені профілі лише за явним фільтром і з виразною позначкою, so that вони не заважали в щоденній роботі.
16. As an Адміністратор платформи, I want to щоб фільтри, пошук і сортування зберігались в адресі сторінки, so that посилання на зріз можна було відкрити знову.
17. As an Адміністратор платформи, I want to бачити, коли список востаннє оновлювався, і кнопку «Оновити», so that знати, наскільки свіжі кешовані дані.

19. As an Адміністратор платформи, I want to бачити всі поля профілю: назву, опис, адресу, координати, телефон, email, часовий пояс, буфер між Записами, горизонт бронювання, колір бренду, коротке посилання, so that відповісти на будь-яке питання про Салон.
20. As an Адміністратор платформи, I want to редагувати назву, опис, адресу, контактний телефон салону, буфер, горизонт бронювання, колір бренду, so that виправити помилку на прохання Власника салону.
21. As an Адміністратор платформи, I want to щоб email, телефон і пароль акаунта були лише для читання, so that я випадково не зламав вхід людині.
22. As an Адміністратор платформи, I want to щоб при збереженні надсилались лише змінені поля, so that не затирати те, чого я не чіпав.
23. As an Адміністратор платформи, I want to отримати повідомлення «дані змінились, перезавантажте», якщо Власник салону змінив профіль, поки я редагував, so that не знищити його правку мовчки.
24. As an Адміністратор платформи, I want to бачити Години роботи Салону по днях тижня й редагувати їх, so that виправити розклад.
25. As an Адміністратор платформи, I want to отримати відмову з поясненням, якщо нові Години роботи порушують закон домену (жодного відкритого дня, вікно коротше 60 хв, Робочий графік Майстра виходить за межі), so that розуміти, що саме треба виправити спершу.

27. As an Адміністратор платформи, I want to відкрити Майстра салону з Ростеру й бачити вкладки Профіль · Робочий графік · Копії послуг · Записи · Відгуки, so that працювати з ним у контексті його Салону.
28. As an Адміністратор платформи, I want to редагувати спеціалізацію, комісію й горизонт бронювання Майстра салону, so that виправляти дані Ростеру.
29. As an Адміністратор платформи, I want to вилучити Майстра з Ростеру з обов'язковою причиною, so that розірвати співпрацю, коли сторони не можуть зробити це самі.
30. As an Адміністратор платформи, I want to щоб вилучення працювало й у Видаленому Салоні, so that звільнити Майстрів, що застрягли прив'язаними до мертвого салону.
31. As an Адміністратор платформи, I want to щоб кнопки вилучення не було у Власника-майстра, so that не ламати інваріант домену.
32. As an Адміністратор платформи, I want to щоб не існувало способу додати Майстра в Ростер повз Інвайт, so that закон «співпраця починається лише з Інвайту» не мав винятків.
33. As an Адміністратор платформи, I want to бачити Інвайти Салону з їхніми статусами й строком дії, so that розібратись, чому Майстер «не отримав запрошення».
34. As a Майстер, I want to отримати сповіщення, коли Адміністратор платформи вилучив мене з Ростеру, so that розуміти, чому я став Незалежним майстром.

36. As an Адміністратор платформи, I want to створювати, редагувати й деактивувати послуги Каталогу, so that допомогти Власнику салону навести лад.
37. As an Адміністратор платформи, I want to бачити біля кожної послуги, скільки Майстрів мають її Копію, so that розуміти наслідки зміни.
38. As an Адміністратор платформи, I want to бачити явне попередження, що зміна ціни чи тривалості в Каталозі не змінює Копії майстрів, so that не думати, що я оновив ціни всім.
39. As an Адміністратор платформи, I want to бачити Копії послуг конкретного Майстра салону з їхніми цінами й тривалістю та редагувати їх, so that виправити ціну саме там, де її бачить Клієнт.

41. As an Адміністратор платформи, I want to щоб нову послугу можна було оцінити лише в MDL, so that діяло те саме правило, що й для бізнесу.
42. As an Адміністратор платформи, I want to бачити Категорії послуг і спеціалізації як довідники лише для читання, so that знати допустимі значення.

### Блокування

53. As an Адміністратор платформи, I want to Заблокувати Салон, Незалежного майстра чи Клієнта з обов'язковою причиною, so that прибрати недоброчесний профіль без знищення даних.
54. As an Адміністратор платформи, I want to бачити в діалозі Блокування кількість майбутніх Записів профілю, so that свідомо вирішити, що з ними робити.
55. As an Адміністратор платформи, I want to щоб Блокування саме не скасовувало жодного Запису, so that рішення про Клієнтів лишалось за мною.
56. As an Адміністратор платформи, I want to зняти Блокування з причиною, so that повернути профіль у роботу після вирішення проблеми.
57. As an Адміністратор платформи, I want to бачити на картці Заблокованого профілю, коли й чому його заблоковано, so that не шукати це в Журналі дій.

59. As a Клієнт, I want to не бачити Заблокований Салон чи Майстра в пошуку й не могти створити до них новий Запис, so that не потрапити до проблемного бізнесу.

61. As a Заблокований Клієнт, I want to могти увійти й бачити свої Записи, але не створювати нові, so that розуміти свій стан.

## Implementation Decisions

### Два репозиторії, один контракт

- Робота ділиться між `bookme-backend` (новий сервіс `admin-api`) і `beauty_admin` (UI). Єдина межа між ними — HTTP-контракт `/admin/*`. UI не має власного бекенду й не звертається ні до DynamoDB, ні до інших сервісів напряму (ADR-0001).
- Контракт `/admin/*` описується новим плейбуком `admin.md` у конституції бекенду; ця специфікація — джерело для нього. Спільна бібліотека бекенду отримує нову роль `admin` у типі ролей і відповідній Zod-схемі (наявний тест, що стверджує протилежне, оновлюється).
- Робота йде вертикальними зрізами, кожен = ендпоінти + екран: 1) каркас і вхід → 2) список і картка Салону (читання) → 3) редагування профілю + Журнал дій → 4) Ростер, послуги, графіки → 5) Незалежні майстри → 6) Блокування + масове скасування → 7) Записи → 8) Відгуки, фото й сертифікати → 9) Клієнти → 10) Дашборд.

### Сервіс `admin-api`

- Четвертий сервіс у монорепозиторії бекенду за зразком трьох наявних: Serverless, Lambda за HTTP API, Middy-ланцюжок зі спільної бібліотеки, той самий конверт відповіді, відмови — кинуті 4xx зі стабільними кодами.
- Кожен хендлер вимагає роль `admin`. Ідентифікатор сутності береться **зі шляху**, ніколи з токена. Шляхи дзеркалять salon-api й master-api: `/admin/salons/{salonId}/…`, `/admin/salons/{salonId}/masters/{masterId}/…`, `/admin/masters/{masterId}/…`, `/admin/clients/{clientId}/…`, `/admin/appointments/…`, `/admin/reviews/…`, `/admin/audit`, `/admin/stats/…`.
- Хендлери — тонкі обгортки: ті самі Zod-схеми й ті самі сервіси домену, що в salon-api / master-api. Де сервіс сьогодні живе всередині одного сервісу й приймає ідентифікатор параметром, він переноситься у спільну бібліотеку, а не копіюється. Жоден інваріант домену для адміна не послаблюється.
- Свідомо **відсутні** ендпоінти: створення Салону чи Майстра, додавання в Ростер повз Інвайт, видалення Власника-майстра, створення Записів, редагування тексту відгуку, завантаження зображень, редагування профілю Клієнта, зміна email / телефону / пароля акаунта, зміна довідників, відновлення Видаленого акаунта.
- Перевірка «акаунт Видалений», яка сьогодні відмовляє у вході, на адміна не поширюється як на ціль: адмін читає Видалені профілі, але всі записувальні дії над ними відхиляються — **крім** вилучення Майстра з Ростеру й скасування Записів.
- CORS — allowlist лише origin-ів адмінки. Значення змінених полів не потрапляють у логи CloudWatch.

### Автентифікація

- Той самий Cognito-пул, користувач із `custom:role = admin`, створюється вручну; самореєстрації немає; TOTP MFA обов'язковий. UI використовує Amplify Auth, як мобільний додаток, і передає ID-токен у заголовку `Authorization`.
- UI перевіряє роль після входу й відмовляє будь-кому, крім `admin`; бекенд перевіряє її незалежно на кожному запиті.

### Списки (ADR-0002)

- Списки Салонів, Незалежних майстрів і Клієнтів будуються Scan-ом таблиці з фільтром на рядки профілів, проєкцією лише потрібних для таблиці полів, і кешуються на боці `admin-api` на кілька хвилин; відповідь несе час побудови. Параметр примусового оновлення обходить кеш.
- Список віддається цілком; пошук, фільтрація, сортування й пагінація — у браузері. Стан таблиці живе в query-параметрах адреси.
- Наскрізні списки Записів і відгуків **не** скануються: вони завжди вимагають діапазон дат або конкретну сутність і йдуть через наявні GSI клієнта / Майстра / Салону. Наскрізний перегляд Записів «за датою по всій платформі» обслуговується тим самим механізмом, що й Детальна статистика.

### Блокування

- Новий стан на профілях Салону, Майстра й Клієнта: `blockedAt` і `blockedReason`. Поле `isActive` для цього **не** використовується — воно лишається за видаленням акаунта.
- Бекенд вважає профіль видимим і придатним до бронювання лише коли він активний **і** не Заблокований. Перевірка додається в ті самі місця, де сьогодні перевіряється `isActive`: пошук і його проєкція, discovery й топ-майстри, сторінки деталей, доступність слотів, створення Запису клієнтом. Блокування позначає лістинг «брудним» для пошукової проєкції.
- Заблокований акаунт **проходить** автентифікацію. Відповідь профілю в salon-api / master-api / client-api отримує поля стану Блокування, щоб додатки показали банер із причиною. Заблокований Клієнт отримує відмову з новим стабільним кодом помилки при створенні Запису.
- Блокування Салону не змінює стан його Майстрів; вони недоступні для бронювання, бо недоступний Салон.
- Зміни в мобільному додатку (банер, переклади нового коду помилки й нових сповіщень чотирма мовами) — окрема задача в репозиторії додатку, яку ця специфікація лише породжує.

### Журнал дій

- Незмінні рядки в тій самій таблиці, без TTL: одна партиція на ціль (для вкладки «Історія») і глобальний індексний ключ за часом (для екрана Журналу). Операцій зміни чи видалення для них не існує.
- Рядок містить: ідентифікатор адміна, тип і ідентифікатор цілі, контекстний Салон (якщо є), тип дії, час, перелік змінених полів зі старим і новим значенням, причину, а для масових дій — перелік зачеплених сутностей.
- Запис у Журнал відбувається **в одній транзакції** зі зміною там, де зміна вже транзакційна, і одразу після успішної зміни — в інших випадках. Відхилена дія рядка не створює.
- Diff рахується одним спільним модулем: «стан до» + «стан після» → перелік змінених полів. Обов'язковість причини визначається типом дії й перевіряється схемою запиту.

### Редагування й конкуренція

- Усі редагування — PATCH лише змінених полів. Запит несе `updatedAt`, який бачив адмін; якщо в базі він уже інший, бекенд відмовляє новим стабільним кодом конфлікту, а UI пропонує перезавантажити форму.
- Умова перевіряється самим записом у DynamoDB, а не читанням перед ним.

### Відгуки

- Відгук отримує стан прихованості: час, причину. Прихований відгук зникає з усіх клієнтських стрічок. Lock «один відгук на Запис» не звільняється.
- Рейтинг і кількість відгуків профілю **перераховуються з нуля** з видимих відгуків, а не «віднімаються» з поточного середнього — це прибирає накопичення похибки й наявний ризик `NaN`. Запис агрегату — з тим самим оптимістичним блокуванням за лічильником, що вже використовується при створенні відгуку.

### Масове скасування Записів

- Одна дія над профілем: скасовує всі його майбутні Записи зі статусом «заброньовано», звільняє слот-lock-и, надсилає кожному Клієнту звичайне сповіщення про скасування й створює **один** рядок Журналу. Операція ідемпотентна й повідомляє, скільки Записів скасовано й скільки не вдалося.

### Сповіщення про втручання

- Нові типи сповіщень — лише для важких дій: Блокування й зняття Блокування, видалення фото чи сертифіката, приховання відгуку. Вилучення з Ростеру використовує наявний тип сповіщення про вилучення Майстра Салоном. Звичайні правки полів сповіщень не породжують.

### Детальна статистика (ADR-0003)

- Базові показники рахуються з того самого кешованого списку профілів, що й таблиці, тож доступні одразу.
- Детальна статистика — окрема функція, що сканує всю таблицю й агрегує в пам'яті. Оскільки повний Scan може перевищити 30-секундний ліміт HTTP API, вона запускається асинхронно: запит старту повертає ідентифікатор обчислення, UI опитує стан, результат зберігається одним рядком конфігурації з часом побудови й лишається доступним до наступного запуску. Одночасно виконується не більше одного обчислення.
- Агрегація — чистий модуль: потік рядків + «зараз» + часовий пояс → структура статистики. Він не знає про DynamoDB. Правила: день — за `Europe/Chisinau`; Вартість Записів виключає скасовані й «не з'явився», ділиться на минулу й заброньовану наперед, конвертується в MDL за поточним курсом наявного сервісу курсів; топи — 10 позицій за 30 днів за кількістю Записів; погані відгуки — оцінка ≤ 2 за 7 днів; «Потребують уваги» — п'ять незалежних ознак.
- Прихований відгук не враховується в блоці якості; Видалені й Заблоковані профілі рахуються у своїх лічильниках, але не потрапляють у топи.

### UI

- Angular 20 (standalone-компоненти, signals + RxJS-сервіси, без NgRx), Tailwind 4, PrimeNG для таблиць, форм, календаря й діалогів. Десктопний веб; на вузьких екранах достатньо, щоб нічого не ламалось. Статичний деплой, окремий на кожне середовище.
- Один модуль доступу до `/admin/*` із типізованими клієнтами за розділами; один перехоплювач для токена, конверта відповіді та відображення кодів помилок у перекладені повідомлення. Незнайомий код показується як є, а не ковтається.
- i18n — власний сервіс перекладу з паритетом ключів між uk / ru / ro, за зразком мобільного додатку; переклади статусів, Категорій послуг, спеціалізацій і днів тижня переносяться звідти. Дати й час форматуються в часовому поясі закладу, не браузера.
- Один перевикористовуваний діалог «дія з причиною» для всіх важких дій; одна перевикористовувана картка профілю, яку Салон і Незалежний майстер наповнюють різним набором вкладок; редактор Робочого графіка спільний для Майстра салону й Незалежного майстра.
- Кожна вкладка картки має власну адресу, щоб на неї можна було дати посилання.

## Testing Decisions

- **Один шов — HTTP-контракт `/admin/*`, перевірений з обох боків.** Добрий тест описує поведінку, видиму крізь цей шов: «такий запит → така відповідь і такий стан», а не те, які функції викликались усередині. Тест не повинен ламатись від рефакторингу, який не змінює контракт.
- **Бекенд — Jest на рівні хендлерів `admin-api`**, за зразком наявних тестів salon-api й master-api. Кожен записувальний ендпоінт перевіряється на: успішну зміну; відмову без ролі `admin`; відмову при порушенні закону домену з правильним кодом; рядок Журналу дій із правильним diff-ом і причиною; відсутність рядка Журналу при відмові; конфлікт за `updatedAt`. Окремо: Заблокований профіль зникає з клієнтського пошуку й відмовляє в новому Записі, але власник проходить автентифікацію; вилучення з Ростеру працює у Видаленому Салоні; масове скасування звільняє слот-lock-и й пише один рядок Журналу; приховання відгуку перераховує рейтинг і не звільняє lock.
- **UI — Playwright проти зібраної адмінки з перехопленням мережі на `/admin/*`**, за зразком e2e мобільного додатку. Сценарії йдуть за user stories: вхід і відмова не-адміну, пошук і фільтри в списку, редагування з PATCH лише змінених полів, конфлікт редагування, діалог із обов'язковою причиною, відображення коду помилки перекладеним повідомленням, перемикання мови, клікабельні плитки дашборда, запуск і опитування Детальної статистики.
- **Юніт-тести — лише для двох чистих модулів**, де комбінаторика надто велика для шва: агрегація статистики (межі дня в `Europe/Chisinau`, перехід на літній час, виключення статусів, змішані валюти, порожня таблиця) і diff для Журналу дій (вкладені об'єкти, масиви, поле зникло, поле з'явилось, без змін). Прототип для них — наявні юніт-тести утиліт спільної бібліотеки бекенду.
- Паритет ключів перекладу між uk / ru / ro перевіряється автоматичним тестом, як у мобільному додатку.
- Компонентні тести окремих Angular-компонентів свідомо не пишуться.

## Out of Scope

- Відновлення Видалених акаунтів і будь-які зміни в наявній логіці видалення акаунта.
- Виправлення наявного бага, через який видалення Салону не звільняє його Ростер, — робиться окремо в бекенді. Адмінка дає лише ручний обхід (вилучення з Ростеру).
- Остаточне стирання чи анонімізація персональних даних, строки зберігання.
- Кілька адміністраторів із різними правами, рольова модель, самореєстрація адмінів.
- Доступ Власників салонів до адмінки в будь-якому вигляді.
- Створення Салонів і Майстрів з нуля, онбординг «замість власника», передача власності Салоном.
- Премодерація й черга схвалення нових профілів.
- Редагування довідників (Категорії послуг, спеціалізації) з адмінки.
- Зміна email-а, телефону чи пароля акаунта; усе, що стосується Cognito, окрім входу адміна.
- Завантаження фото, редагування тексту відгуків, створення Записів, редагування профілю Клієнта.
- Платежі, підписки, комісії платформи — їх у системі немає.
- Нічні знімки статистики, DynamoDB Streams, розріджений GSI для списків — відкладені до спрацювання тригерів з ADR-0002 і ADR-0003.
- Фільтр дашборда за містом; експорт даних; push-оновлення цифр на відкритому екрані.
- Мобільна верстка адмінки.
- Реалізація банера Блокування й перекладів у мобільному додатку — окрема задача в його репозиторії.

## Further Notes

- `beauty_admin` зараз порожній (лише документація агентів), тож перший зріз включає створення самого Angular-застосунку.
- У бекенді dev і staging ділять один Cognito-пул і одну таблицю; адмінка для dev працює з обома одразу — індикатор середовища в шапці має це відображати чесно.
- Плейбук `accounts.md` у конституції бекенду стверджує, що видалення акаунта чистить Cloudinary; код цього не робить. Фото Видалених профілів існують і видимі адміну.
- Статус «завершено» в бекенді ніхто не ставить автоматично — лише відгук Клієнта. Тому більшість проведених візитів лишаються «заброньовано» в минулому; визначення Вартості Записів це враховує, а графік Записів за статусами має показувати такі Записи окремою категорією, а не видавати їх за майбутні.
- Скрипт очищення осиротілих email-lock-ів і скрипт очищення застряглих профілів Майстрів уже існують у бекенді; дія вилучення з Ростеру має давати той самий кінцевий стан, що й другий із них.
- Вартість Scan-ів росте з кількістю Записів у таблиці, а не Салонів. Обидва тригери перегляду (ADR-0002, ADR-0003) варто перевіряти разом.
